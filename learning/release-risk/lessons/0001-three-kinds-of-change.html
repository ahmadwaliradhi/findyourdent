Lesson 1 · Release risk for FindYourDent

Three kinds of change

Before you deploy anything on top of a live build, ask one question: what does this change do to things that already exist? The answer sorts every change into one of three kinds, and each kind has its own deploy rule.

The three kinds

KindWhat it touchesDeploy rule
AdditiveNew optional field, new page, new filter. Old data stays valid and keeps its meaning.Deploy any time. Old documents simply lack the field.
SemanticSame data, new meaning. A number shown to users is computed under a new rule.Decide what existing users will see the moment it lands. Recompute is a data migration.
ContractThe shape two services exchange changes.Expand, migrate, contract: both shapes valid first, then switch, then remove the old one (Fowler, Parallel Change).

Firestore is schemaless, so old and new document shapes sit side by side without errors (Firestore docs). That makes additive changes cheap and hides semantic ones: nothing fails, the meaning just changes.

Why #105 is the dangerous one

Semantic. Today a Proof of Visit is optional and every published Testimony counts. After #126, a Provider needs three Proven Testimonies before any star average shows; otherwise it reads "Belum cukup testimoni terbukti". The 30 Testimonies from H10 (#30), spread across many cities, will mostly be one or two per Provider and mostly without proof. On release, nearly every star on the site disappears, in the middle of judging.

The cheap fix hides in the spec. Testimonies "already marked Kunjungan terbukti under the old 24-month rule stay accepted" (spec 09). Ask the H10 recruits to attach their receipt now, on v0.2.2, and their Testimonies survive the switch.

Contract. deploy.sh agent runs first. If the new agent sends extracted facts while the old web service still reads proofOfVisit, every proof check breaks for the minutes between the two deploys. Ship an agent that sends both shapes first.

One more trap: the deploy script itself

infra/gcp/deploy.sh runs gcloud run deploy with no --no-traffic, then the smoke test. A bad revision serves judges before the smoke test can catch it. Cloud Run lets you deploy with no traffic, test the revision on a tag URL, then move traffic, and roll back by moving traffic back (Cloud Run docs). New composite indexes also fail queries until they finish building (Firestore docs), so deploy indexes a day ahead.
